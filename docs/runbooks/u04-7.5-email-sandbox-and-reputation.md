### Parte B · Caída de reputación o ráfaga de rebotes y quejas

1. **Pausar el envío del conjunto de configuración**. Detiene el correo **sin tocar la aplicación**:

   ```text
   aws sesv2 put-configuration-set-sending-options --configuration-set-name vigia-email-pilot --no-sending-enabled
   ```

   Los envíos fallan, el cortacircuito del correo de cada proceso se abre y los avisos quedan visibles en la aplicación con `degraded_app_only` (`failure_code` `email_circuit_open`); nada se pierde (BR-LAZ-130). La alerta de integridad comprometida se sigue encolando con el circuito abierto (BR-LAZ-127) y además llega por la alarma `vigia-integrity-compromised` de U-02.
2. **Revisar el tope propio**: 200 correos de resumen por hora y organización (NFR-LAZ-13). Si la ráfaga viene de un bucle de la aplicación, el tope ya la frenó y el panel «Correo (U-04, n 23)» lo muestra como una meseta por organización.
3. **Identificar la ráfaga** en el panel «Correo (U-04, n 23)»: `email_messages_total` por `organization_id` y `email_state` (`bounced`, `complained`). Un rebote duro masivo en una sola organización suele ser una lista de usuarios importada con direcciones inválidas; una queja masiva, un aviso que los usuarios no esperan. Las unidades de cada estado son distintas ([métricas de U-04](u04-metrics.md#fuentes)): no se suman entre sí.
4. **Comprobar las marcas**. El consumidor `email_delivery_events` marca solo a cada usuario: rebote duro → `EmailMessage` `failed` con `bounce_kind = hard`; queja → silencia sus niveles `normal` y `digest`. **Ninguna supresión alcanza el nivel `immediate`**: la entidad no tiene campo para silenciarlo (BR-LAZ-126). Con el consumidor parado, se sigue el camino B del [runbook 7.2](u04-7.2-dead-letter-replay.md).
5. **Corregir el origen** con el administrador de la organización (direcciones corregidas, usuarios dados de baja). Con `email-send-quota-high` sin ráfaga, la causa es crecimiento: se pide más cuota al proveedor y se ajusta `EMAIL_DAILY_SEND_QUOTA` (parte A, paso 4).
6. **Reanudar** cuando la tasa baje del umbral en dos evaluaciones consecutivas:

   ```text
   aws sesv2 put-configuration-set-sending-options --configuration-set-name vigia-email-pilot --sending-enabled
   ```

   El cortacircuito de cada proceso se cierra solo con el siguiente envío correcto. Los avisos degradados durante la pausa no se reenvían: siguen en la aplicación.

## Vuelta atrás

- **Parte A**: un umbral mal ajustado se corrige con otro PR y otro release; la salida del arenero no se deshace.
- **Parte B**: la pausa se deshace con el paso 6 en cualquier momento. Si el proveedor pausó la cuenta entera (`EnforcementStatus` distinto de `HEALTHY`), reanudar el conjunto no basta: hay que responder a su revisión con el plan de corrección.
